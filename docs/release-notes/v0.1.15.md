# The Housekeeping Update

Two new tools arrive — a reverse-engineering workbench and a spyware triage scanner — and three
pieces of housekeeping that were overdue: runtime images that piled up at about 3 GB each are now
swept, the terminal's scrolling has its real cause fixed inside the CLI renderer, and the first
prompt appears in about a second instead of ninety.

## Two new sections in Tools

**Reverse Engineering → mcp-reverse** is a workbench behind one MCP server: native PE, ELF,
Mach-O, DEX, .NET, Unity and Unreal parsers, entropy and packer triage, YARA, x86-64 and ARM64
disassembly and emulation, function diffing, and a searchable 4,256-skill knowledge base. It is
built from a pinned tag on its own Node 24 runtime — the image's Node 22 cannot open its
`node:sqlite` library without an experimental flag — and it runs from a writable copy in the
project's state volume, because it writes its database, caches and audit log beside its own code
while the root filesystem is read-only. The Ghidra, IDA, Binary Ninja, x64dbg and Frida bridges
need those programs on your machine; inside the sandbox they report themselves unavailable, and
the skill says so rather than letting a model promise them.

**Cyber Security → Zero Breach** is a new section, after Reverse Engineering, for published
mercenary-spyware indicators: Pegasus, Predator, Graphite, Candiru and others. Given access to a
computer it checks that computer whole — browser history, cookies and caches, file SHA-256 against
published sample hashes, hosts entries, DNS records and startup entries — and pointed at a phone
or a folder it reads an AndroidQF collection, an iPhone backup, an extracted file system, a
sysdiagnose, or just those files. Scans are read-only, need no administrator and make no network
request: the 29 published indicator sets, about 13,000 indicators when this image was built, are
downloaded at build time and recorded in a manifest, so a scan needs no route out. Inside this
sandbox it can only read what is mounted, so a whole-computer scan is one you run on that
computer; the workspace gets a skill that says exactly that, and a row that names its author,
@archive.genocide on Instagram.

## Your disk stops filling up

Every runtime edit changes the revision in the image tag, which is what forces a rebuild when the
runtime changes — and it also means the image built yesterday can never be run again. At about
3 GB each they accumulated silently: sixteen gigabytes of images on this machine before anyone
looked.

Images are now swept on a rule that is deliberately conservative. An image is kept if it is not
Deepsand's at all, if any project resolves to it *now*, if any container — running or stopped,
ours or not — uses it, if it is younger than an hour, or if Docker will not say when it was made,
because unknown age is not abandonment. Everything else is removed by tag, never with `--force`,
so a container that takes an image mid-sweep simply keeps it, and that refusal is information
rather than an obstacle. The sweep runs four seconds after startup — after the container sweep, so
they do not queue on the same Docker call — and again after a build succeeds, which is the only
moment a new image can orphan an old one while the app stays open. A daemon that does not answer
is an error, never an empty plan: "could not ask" and "nothing to clean" must not look the same
before a deletion.

The base image tag is kept. No project runs it directly, but prebuilding is a supported thing to
do and its layers are shared with every project's tag. That also fixes the "image missing" badge,
which used to watch the base tag — the one the app never builds — and so could say "missing"
permanently while every project's own image was present.

`deepsandctl images [--prune]` prints the same decision with the reason each image is kept, so you
can see what would go before anything does.

## The terminal's third cause

0.1.13 fixed the PTY's birth size; 0.1.14 fixed input that arrived while a start was in flight.
Both were real, and both were symptoms of a third thing. The CLI renders with Ink, and Ink treats
a frame at or over the viewport as fullscreen: it writes `ESC[2J ESC[3J ESC[H` and the whole
static conversation again, `[3J` clears the scrollback, and this repeats on every status tick. A
tall live frame — the process-output panel is up to 30 rows, a session list or a long prompt is
taller — made that constant.

`runtime/bin/patch-deepcode-ink.mjs` now rewrites exactly that branch at image build time. The
predicate is left as upstream ships it; what changes is what the branch writes: no scrollback
clear, the frame's last `rows` lines when it is taller than the screen, the last screenful of
history restored above it when it fits again, and the log told exactly what was drawn. The
invariant is one line: **a repaint writes at most one viewport and never scrolls**. The normal
path is left byte-identical and `--check` asserts it sits unmodified, a renderer whose shape the
patch does not recognise fails the build instead of shipping unpatched, and applying it twice is
harmless.

Two smaller fixes came out of the same investigation. The terminal pane keys its attach effect on
the selected project's *id*, so an ordinary project-list refresh — a session status change, a
broker answer, a container sweep, Docker coming back — no longer resets the screen behind a TUI
that is still running. And the bar above the terminal is now always present: a Run when stopped, a
Stop when running, one ellipsised line, so the pane cannot change height after the PTY was created
and leave a TUI drawing for a box it no longer has.

## The first prompt arrives at once

The CLI builds its `@`-mention index inside the first render, by walking the whole workspace. On a
normal filesystem that is milliseconds. Inside the sandbox the workspace is a bind mount, where
one entry costs milliseconds — measured here, 39,192 entries took 2m35s — so a repository with a
vendored toolchain painted nothing but the entrypoint's banner for about ninety seconds, and the
20,000-item cap was exhausted by `.toolchain` before any real source was indexed.

`runtime/bin/patch-deepcode-mentions.mjs` starts that index empty; the mount effect three lines
below the initialiser already fills it, and refills it when the agent goes idle and when a mention
token first appears. It also skips hidden directories that are tool state while still indexing
`.github`, `.vscode`, `.devcontainer` and hidden files such as `.env.example`. Measured after the
patch, same image and same conversation: the input box is on screen within one second.

## Which renderer did I get?

An installed build derives its image tag from the runtime tree *it* shipped, so an older window
can build a current-looking image from stock scripts and still scroll, with a normal-looking log
and an ordinary tag. `deepsandctl doctor` now prints the runtime tree, its revision and which
patches it applies, and a start logs a warning naming any patch the tree is missing — without a
Docker call. If the old scrolling ever comes back, read that line before re-reading the patch.

## Tests

`npm test` gained the two patch suites and the image build runs them too. The Ink self-test applies
the patch twice, refuses a shape it does not know, and drives a fake terminal to check one viewport
per repaint, no scrollback wipe, no scrolling and nothing lost. The mention self-test runs the
patched scanner against a temporary tree: real source found, `.github` found, a vendored
`.toolchain` and a hidden symlink not.

`npm run app:dev` also frees port 1420 before starting, so a vite left over from an interrupted run
cannot become either a failed launch or, worse, a window on a stale bundle.

## Upgrading

Both new tools and both CLI patches live in the image, so the runtime revision changed: the next
Run rebuilds this project's image, and the sweep above removes the one it replaces after the grace
period. The first rebuild after this update therefore takes the usual few minutes. Nothing in your
projects is modified, and no grant or permission is affected.
