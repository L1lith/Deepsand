# The DeepCode 0.5.0 Update

DeepCode 0.5.0 changed how its CLI is packaged, and the two patches Deepsand applies at
image-build time were still looking for the old layout. The image build failed, so the
sandbox could not start. The automatic CLI refresh uses that same build, so it failed too
and left you on the previous 0.4.5 CLI — which then asked you to update it with npm from
inside a sandbox that cannot install anything. All of that was one cause, and it is fixed.

## DeepCode 0.5.0

`cli.js` is now a small dispatcher; the Ink renderer and the `@`-mention scanner live in
`chunks/cli-app-<hash>.js`. The patches now follow the entry point's relative imports and
patch every reachable bundle that carries them, rather than assuming one file. The package
also ships stale `cli-app` chunks that nothing imports, so a directory scan would have
rewritten files no container reads.

The mention patch also stopped hard-coding esbuild's React namespace (`import_react48`, now
`import_react50`) and its self-test reads the `fs`/`path`/`ignore` shim names out of the
bundle instead of assuming those either. The image build now completes on 0.5.0, and the
host refreshes the CLI before a start as before — so the in-terminal npm prompt is no
longer the first thing you see.

## Ask for a Debian package

The sandbox has no root and a read-only root filesystem, so `apt-get install` inside a
session can never work. The agent can now ask for a package with
`deepsand_request_packages`. The request is an ordinary permission dialog; when you
approve, the packages are stored on the project and installed by the image build as root,
beside the tools.

Names reach an `apt-get install` argument list, so only real Debian binary package names
are accepted: lowercase letters, digits, `+`, `-` and `.`. Anything that looks like an
option, a version pin or an architecture qualifier is refused rather than passed through.
A package the image already carries is reported as already covered and never becomes a
dialog.

The approved list joins the image tag, so approving one moves the tag and the next build
installs it. `deepsand_sandbox_info` reports packages from the image's own
`deepsand.packages` label, which is what the running sandbox actually has rather than what
the project currently asks for.

## Housekeeping

The tools cache no longer records or copies `@vegamo/deepcode-cli`. The version listing is
taken from the finished image, where the CLI's own layer has already installed it, so every
CLI release looked like a moved tool and emptied the entire tools cache. The CLI is
refreshed on its own layer and should never have been cached with the tools.

A failed CLI refresh now says it produced no new image, instead of claiming the image was
rebuilt with a stale CLI.

## Upgrading

The runtime revision changed, so the next Run rebuilds this project's image; the previous
one is swept after the grace period. Nothing in your projects is modified, and no grant or
permission is affected. Approved Debian packages, if you add any, are installed by that
rebuild.
