# The Unstuck Update

Four failures that made the app feel broken are fixed: a permission answer that froze the
window, an attachment that was named but never written, a terminal that repeated itself, and a
cleanup that could delete a sandbox another Deepsand process was still using.

## Granting a secret no longer freezes the app

Pressing **Grant access** on a secret request could leave the whole window frozen with the busy
cursor, and the same dialog came back after every restart. Two bugs in one path caused it:

- the answer took the app's state lock a second time on the same thread. A lock cannot be taken
  twice that way — it waits for itself — and the command ran on the UI thread, so the window
  stopped painting and never came back;
- the secret path never removed the answered request from the spool, so the next tick, and the
  next launch, announced the same decision again, with the sandbox paused behind it.

Now the secret is stored, the answer is written, the request is cleared, and the command runs off
the UI thread. If the value cannot be stored, you get a refusal that says why. A request that
already has an answer is never shown again.

## An attachment that is actually in the sandbox

A pasted image was named at `/home/deepcode/.deepcode/attachments/…`, the path was typed into the
agent's prompt, and the agent correctly reported that there was no such file.

The write ran through `docker exec` as root, but the sandbox drops `CAP_DAC_OVERRIDE`, so root
cannot create a file in a directory owned by uid 1000 — and the script ended in `|| true`, which
turned that failure into success. Nothing had been written.

Every host-to-container write now runs as uid 1000: pasted attachments, dropped files, and the
directory they go in. The scripts no longer swallow failure, and the app checks that the sandbox
can read the file back before it hands over the path. If it cannot, you get a message instead of
a phantom attachment.

## A terminal that stays put

The agent's live footer — status line, rules, input row — could repeat down the screen, each copy
over the last. It looked like the resize loop the previous release guarded against, but nothing
was resizing: the pseudo-terminal was **born at a hard-coded 40×120**, because the pane asks for
its size before a session exists and that request was dropped. A TUI drawing a 40-row frame in a
33-row terminal scrolls on every spinner tick instead of overwriting its last frame.

The size the window asks for is now remembered per project, even with no session, and the
pseudo-terminal is created at that size. A hidden pane's `0×0` is ignored, and the size is
clamped. This applies to the first Run and to every restart.

## Cleanup that only removes its own

The container sweep treated "no session in this process" as "abandoned". That was wrong for
`deepsandctl run` and for a second instance with its own data directory: their sandboxes would
have been removed two minutes after they started.

Every plan and every sharing probe now records the pid that started it, and the sweep removes a
container only when this process started it and no session owns it, or when the process that
started it is gone. Liveness comes from the machine's process table, filtered to Deepsand
executables — a reused pid counts as dead, so a crashed sandbox is still cleaned up. If the
process list cannot be read, every other owner is assumed alive: the wrong answer deletes
somebody's running sandbox.

Activity → Containers still lists everything, marks what is in use and what is abandoned, and
**Remove abandoned** respects the same rule. Containers created before this release have no owner
record, so they are left alone.

## Smaller things

- The documentation shows a real screenshot of the app in each of its seventeen languages.
- Intel Mac builds are in the update manifest again: the release pipeline passes the target to
  every matrix job, so the two macOS builds no longer collide on one artifact name.
- The translator refuses to write a page whose markup it changed, rather than producing a page
  that cannot render.

## Upgrading

If your sandbox image was built from an earlier runtime revision, the first Run of each project
rebuilds it once. Deepsand does that automatically, and the build output appears in the Activity
tab.
