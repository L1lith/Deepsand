# Под капотом

Эта страница предназначена для разработчиков, которым нужна техническая форма системы. Если вы ищете объяснение простым языком, начните с [Что такое Deepsand?](./what-is-deepsand).

## Архитектура

Deepsand — это настольное приложение Tauri с тремя основными уровнями:

- **Окно** — это интерфейс SolidJS. Он отображает состояние и отправляет намерения; оно не решает политику.
- **Слой Тельца** предоставляет команды рабочего стола и преобразует ту же командную поверхность на HTTP-сервер обратной связи для удаленных клиентов.
- **`deepsand-core`** владеет правилами. Проверка пути, план `docker run`, брокер разрешений, выходной прокси, зашифрованное секретное хранилище и хранилище состояний — все это находится там.

Настольное приложение и драйвер командной строки `deepsandctl` используют одно и то же ядро, поэтому они не могут расходиться в решениях по безопасности.

## Один проект, один контейнер

Каждый проект получает свой собственный контейнер Docker и свой том состояния. Каталог проекта монтируется по адресу `/workspace`; другие каталоги хостов требуют явных разрешений.

`policy::plan_run` собирает полную версию аргументов `docker run` в одном месте. На вкладке «Активность» показан именно этот план, включая подключения, возможности, сетевой режим и пути только для чтения.

Контейнер намеренно ограничен:

- Корневая файловая система доступна только для чтения, с размером монтирования tmpfs для `/tmp` и `/run`.
- Катушка ответа и каталог состояния монтируются только для чтения.
- Сокеты среды выполнения контейнера отклоняются по имени.
- Возможности удаляются до запуска DeepCode и устанавливается `no-new-privileges`.
- Сокеты времени выполнения контейнера и другие запрещенные монтирования не закрываются, а не создают более слабый план.

## Разрешения

Песочница может запросить дополнительный доступ, но не может его предоставить. Запрос разрешения записывается в спул; хост-брокер проверяет его и приостанавливает контейнер. Оператор видит запрос и принимает решение.

При утверждении запроса каталога контейнер воссоздается с новым монтированием привязки и возобновляется сеанс. Отказ — это один из двух ответов, и модели сообщается, какой из них: **Не спрашивай больше** является окончательным, а **Не сейчас** на этот раз отказывается и говорит, что модель может спросить еще раз позже. Окончательный отказ сохраняется в проекте и применяется хостом: для пути или чего-либо под ним никогда не создается монтирование, а хост, которому было отказано, становится правилом запрета, охватывающим его поддомены. Блоки указаны в Разрешениях и там их можно снять, потому что решение без пути назад — это ловушка, а не выбор.

Запрос на то, что уже есть в песочнице, отклоняется с объяснением. Автоматического пути утверждения не существует, поскольку молчаливое одобрение будет означать согласие, которое оператор никогда не давал.

## сеть

Сетевая политика имеет четыре режима:

| Режим | Поведение |
| --- | --- |
| `none` | Только конечная точка модели через выходной прокси-сервер Deepsand. |
| `allowlisted` | Конечная точка модели, прокси-сервер и именованные хосты, адреса и порты. |
| `internet` | Доступ в Интернет с блокировкой локальных и частных диапазонов внутри контейнера. |
| `full` | Доступ в Интернет без блокировки локальной сети. |

Запись имени хоста разрешается прокси-сервером, который отклоняет частные, петлевые, локальные и зарезервированные результаты. Запись адреса осуществляется непосредственно контейнером, что позволяет клиенту базы данных или другой программе, отличной от HTTP, подключаться. Именованный порт публикуется только в кольцевой проверке хоста.

## Секреты и обновления

Неактивные секреты шифруются ключом, хранящимся в хранилище ключей операционной системы. Они передаются в контейнер через файл среды, а не как значение командной строки, и внедряются только при запуске песочницы.

Сборки выпусков проверяют подписанные обновления перед их установкой. Ключ подписи никогда не хранится в репозитории.

## Командная строка

`deepsandctl` обеспечивает поверхность без головы:

```bash
deepsandctl doctor
deepsandctl plan <project> --offline
deepsandctl run <project>
deepsandctl watch <project>
deepsandctl requests <project>
deepsandctl network <project> <mode>
```

`plan --offline` печатает точный аргумент `docker run` без запуска контейнера, что полезно для просмотра измененной политики.
